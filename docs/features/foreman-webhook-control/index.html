Foreman-controlled webhook nodes

Let the foreman create, configure, connect, inspect, and retire webhook nodes within explicit ownership and quota boundaries.

What changes

The active Foreman can build an externally triggered workflow without asking the operator to configure each hook by hand. The same guarded CLI can create, inspect, update, rotate, connect, and retire a source-only webhook.

Every agent-side decision is bound to the Foreman’s immutable GUID. Hook URLs, token material, templates, and recognizable secret aliases are recursively removed from audit arguments.

What stays human

  • Plain agents cannot read or mutate hook capabilities.
  • Executable transforms remain human-only.
  • Human-created and other Foremen’s hooks remain outside the ownership envelope.
  • Revoked or deleted owners leave live hooks for operator recovery.
  • Internet tunneling and provider-specific signatures remain separate features.

From intent to durable delivery

1 · Grant

A human appoints the Foreman

Crew resolves the live managed caller through its anti-spoofing identity path.

2 · Create

The Foreman creates a hook

The guarded write records the creator’s immutable GUID, starts unblessed, and returns the capability only to the authorized caller.

3 · Connect

A finite route targets an owned agent

The hook is a source only. Its edge must stay within the ownership envelope and configured positive ceilings.

4 · Deliver

An external POST becomes agent mail

The existing webhook path creates one durable receipt and message with immutable hook, edge, and target provenance.

5 · Review

The operator can bless the graph

Unblessed hooks and routes remain visible for review through the existing graph-aware blessing controls.

6 · Rotate or recover

Capabilities remain deliberately owned

The exact owner can rotate or remove its hook. After revocation or deletion, control falls back to the human without interrupting delivery.

One guarded path, two durable records

Ownership is an immutable GUID

Display names are context, never authority. Renaming cannot redirect control, and a same-name replacement receives a new GUID with no access to the old hook.

Revocation does not break integrations

The hook, routes, receipts, and capability remain live. Agent management is denied immediately, while the human can inspect, rotate, bless, or remove the orphan.

The last quota slot is serialized

CREW_MAX_WEBHOOKS_PER_FOREMAN defaults to 12. Invalid configuration falls back to the default, and admission cannot race past the exact indexed count.

Audit history is not a secret store

Nested mappings, lists, mapping keys, cycles, and hostile objects are sanitized before persistence. Applied secret reads record the decision, not the returned capability.

Public surface and lifecycle

Foreman-capable commands

crew webhook create <name> [--description TEXT] [--template TEXT]
crew webhook list
crew webhook show <name>
crew webhook update <name> [--description TEXT] [--template TEXT]
crew webhook rotate <name>
crew webhook remove <name>
crew connect <hook> <agent> --max-turns N --token-cap N --cost-cap N

Operator controls

crew bless <hook>
crew bless --edge <hook> <agent>
crew bless --all

list omits URLs and token material. show is a guarded, audited secret read. Create, update, rotate, and remove all use the same immutable ownership boundary.

Stored authority

created_by      = display name at creation
created_by_guid = immutable Foreman GUID
blessed         = false

The GUID controls authority. Removing an owned hook releases one quota slot; historical messages and receipts keep their immutable provenance.

Security and failure boundaries

Authority and disclosure rules

  • Plain agents are default-denied for hook secret reads and mutations.
  • Every privileged action requires a live Foreman flag and exact created_by_guid match.
  • Caller names and hook names are not authorities.
  • list never emits a URL; secret-bearing commands print only after authorization.
  • Routes remain source-only, finite, ownership-bounded, and transform-free.
  • Refusal reasons are generic and never interpolate stored hook rows.

Deliberate non-goals

  • No hook management for plain agents.
  • No cross-owner or human-created hook control.
  • No executable edge transforms or inbound hook edges.
  • No bypass of the finite edge-cap policy.
  • No Internet tunnel or provider-specific signature validation.

Failure behavior is explicit and recoverable

Failure Visible behavior Recovery
Caller is not the active Foreman The command fails without exposing a URL or changing the hook. The human grants Foreman authority.
Hook belongs to another authority The command fails outside the ownership envelope. The human owner performs the action.
Hook quota is full or races Creation fails before a capability is returned; only one contender can commit the last slot. Remove an owned hook or raise the configured limit.
Owner is revoked, deleted, or replaced by name The hook stays callable, while agent-side management is denied. The human manages the orphan; a different GUID never inherits it.
Template or storage is invalid No partial hook change or false success is reported. Correct the template or restore storage, then retry.

Additive rollout, data-preserving reversal

Rollout

The feature reuses the additive creator GUID and blessing fields already present on graph nodes. Human-created hooks keep their existing behavior. Existing finite edge and webhook lifecycle invariants remain authoritative.

Reversal

Removing the Foreman guard cases and CLI authority returns hook management to human-only operation without deleting hooks, routes, receipts, messages, or public capabilities.
