Harness introspection

One Harness interface that reads, uniformly across coding harnesses, the open goals each agent is working toward — implemented by Claude Code, Codex CLI, and Hermes readers.

User flow

Start state

Crew shows whether an agent is up and, if the agent bothered to say so, what it claims to be doing (crew activity). Neither answers the question an operator of a standing crew actually asks: which of these agents is pursuing a goal right now? That record exists — but it lives inside each agent's coding harness, in a completely different shape per harness (per-session task files, a thread-goal sqlite, a kanban board), and Crew never read any of them.

Outcome

crew harness answers it for every agent in one vocabulary. A Harness base class captures only what Crew wants to show the user — the open goals — and three clients implement it: Claude Code, Codex CLI, and Hermes, each read from the harness's own durable state with no cooperation from the agent. A runtime Crew has no reader for says exactly that, rather than reporting an empty goal it cannot vouch for.

$ crew harness
  AgentA
      goal: rebuild the search index  (+2 more open)
  hermes-worker
      goal: triage inbound bugs
  toolbox: Custom command has no goal state Crew can read

Architecture

Public interface

Commands and APIs

  • crew harness [NAME] — the open goals for every agent, or one.
  • crew harness --json — the same reading as machine output, one object per agent.
  • crew.harness.probe(agent) / probe_many(agents) — the Python seam, returning a frozen HarnessState (runtime, supported, goals, goal, goal_count, reason).
  • crew.harness.Harness — the base class. Its responsibility is only what Crew shows the user; a client implements read_goals(home) and registers in HARNESSES. Adding a harness changes nothing else.
  • crew spawn-agent --runtime hermes — Hermes joins claude/codex/custom as a first-class runtime (adapter, launch command, process match, identity.md-only publication).

Data and lifecycle

  • Crew stores nothing: there is no schema change, no new field, and no migration. Every reading is derived at call time from the harness's own files.
  • The only retained state is a short-TTL per-process cache of the ps sweep and Claude's session registry, rebuildable and cleared with claude.reset_caches().
  • Nothing under any harness's state directory is ever written; sqlite stores are opened read-only with a 200 ms budget. CREW_CLAUDE_STATE_DIR, CREW_CODEX_STATE_DIR, and CREW_HERMES_STATE_DIR relocate where Crew reads from.

Security and failure boundaries

Authority

  • Read-only, and only files the operator already owns. No new network surface, no new port, no new stored credential.
  • Goal text is operator content. It is capped at 200 characters (the same cap as an agent's activity line) and stays on operator-facing surfaces; the public hook gateway serves none of it.
  • A Claude session id is validated before it is joined into a path, so a malformed registry entry cannot walk Crew out of the state directory. Codex and Hermes sqlite queries are parameterized and open their stores read-only.

Failure behavior

  • The probe never raises: it runs inside the dashboard poll, and every unreadable, absent, or malformed input degrades to an empty reading carrying a reason.
  • "Cannot read" and "nothing set" are different answers. supported=False is reserved for a runtime Crew has no reader for, so the UI can never badge such an agent as goal-less.
  • This reads other products' private layouts by design — the accepted trade for needing no agent cooperation. tests/test_harness_live.py is the canary: run against the real installs, it fails the moment Claude Code, Codex, or Hermes moves its files. Codex already versions its stores (goals_<N>.sqlite), so the reader follows the newest generation.
  • Cost is bounded on purpose: one cached ps sweep and registry read serve a whole dashboard poll, sqlite opens carry a short timeout so a mid-write harness costs a reading rather than a stalled poll, and every list is capped (50 goals, 200-char text).

Rollout and reversal

Purely additive: one new package, one new CLI subcommand, one new runtime key, no schema change and no stored data. Existing agents gain the reading without being restarted or reconfigured, and agents on a runtime Crew cannot read are reported as such instead of silently blank. Reversal is deleting crew/harness/, the harness subparser, and the hermes adapter — nothing persists that would need cleaning up.

Engineering inventory and redaction notes

Declared code: crew/harness/ (the base class and the Claude Code, Codex, and Hermes readers), crew/runtime.py and crew/config.py (the hermes adapter and launch default), crew/identity.py (runtimes with no native instruction file publish identity.md only), crew/cli.py (the harness subcommand), README.md. Declared tests: tests/test_harness.py drives synthetic state directories for all three harnesses — session registry and task files for Claude Code, goal/thread sqlite stores for Codex, a kanban sqlite for Hermes — written per test and deleted in cleanup; no test touches the operator's real state directories. tests/test_harness_live.py is opt-in (CREW_RUN_HARNESS_LIVE=1), read-only against the real installs, and skips rather than fails when a harness is absent.

Redaction: the live tests assert on shapes and counts and never print goal text, because a goal is operator content. The evidence capture was taken against throwaway fixtures (a kanban card and a task list created and removed for that purpose), so no real objective appears in it.
